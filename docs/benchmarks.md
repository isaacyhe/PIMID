# Benchmarks

49 self-contained benchmarks across 7 suites, all with ROI markers
(`zsim_roi_begin/end`) and four input-size tiers (tiny/small/medium/large):

| Suite | Benchmarks | Parallelism |
|---|---|---|
| PIM kernels (9) | stream_triad, vector_add, gemv, spmv_csr, bfs, histogram, reduction, stencil_2d, pointer_chase | serial + OpenMP + MPI |
| BabelStream (1) | babelstream | OpenMP |
| Rodinia (10) | hotspot, needle, pathfinder, srad, kmeans, lud, backprop, lavamd, particlefilter, myocyte | OpenMP |
| Classic (6) | dhrystone, whetstone, binary_search, quicksort, sha256, naive_matmul | serial |
| NPB (5) | IS, CG, EP, MG, FT | OpenMP / MPI |
| SPLASH-3 (12) | FFT, Radix, Barnes, Ocean, LU, Water-Nsq, Water-Sp, Cholesky, FMM, Radiosity, Raytrace, Volrend | pthreads |
| PARSEC (6) | blackscholes, canneal, streamcluster, swaptions, fluidanimate, freqmine | pthreads |

Additionally:
- `benchmarks/host/` -- host-side variants of the core kernels.
- `benchmarks/hostphase/` -- the host phases (input generation, result handling) of the core kernels, without device computation.

Co-simulation has no separate workload family: any ordinary ROI-marked
workload runs in co-simulation (a configuration with `system.hosts[]`). Its ROI region executes on the
device PEs, the out-of-ROI code on the host, and the boundary costs (launch,
coherence flush, and the two-layer host<->device bridge) are charged
explicitly (see [cosim.md](cosim.md)).

### The paper's co-simulation experiment (Fig. 5)

The co-simulation figure compares PIM offload against conventional multicore
scaling, both measured over the **task region** ("inputs ready in host mem"
-> "results visible in host mem"), never kernel-only or whole-process:

- **Techs:** HBM3 (bandwidth-rich interposer host, `native/interposer`) and
  DDR5 (commodity bus host, `native/pcb`). Host HBM3 has no idle-latency edge
  over DDR5 -- only bandwidth -- so the contest is PIM latency-elimination vs
  host bandwidth-abundance.
- **Kernels (5):** `stream_triad`, `gemv`, `bfs`, `stencil_2d`, `histogram`
  (the near-data-prep sweep set; see below).
- **APIs (2):** OMP and MPI (the 1.6 thread-MPI stack; MPI cells run coupled).
- **Co-simulation cells:** single OoO@2GHz host + device (8 `alu_core` PEs @ BANK,
  same tech) -> 2 techs x 5 kernels x 2 APIs = 20 cells.
- **Baseline cells:** host-only, **same tech as the paired co-simulation cell** (no
  host-tech confound), 1/4/16 OoO cores x {OMP, MPI}, via
  `PIMID_COSIM_NO_OFFLOAD=1` on the same binary -> 2 x 5 x 3 x 2 = 60 cells.
  1-core cells subsume the old serial baseline; 1-core MPI = a single rank on
  the thread-MPI runtime.

The three baseline configs are `examples/cosim/baseline_host_{1,4,16}core.yaml`
(see [examples.md](examples.md)); the experiment sets
`memory.technology` per cell.

```bash
make -C benchmarks all        # build everything
```

Per-benchmark run configs live with each suite: `pim_kernels/<k>/*.yaml`
(per-kernel, per-size-tier), `npb/configs/`, `splash3/configs/`,
`parsec/configs/`; rodinia and classic configs are generated by
`benchmarks/gen_rodinia_classic_configs.sh`.

## Data-model variants

The core kernels come in **three data-model variants**:

| variant | parallel workers share data via | models |
|---------|---------------------------------|--------|
| `serial` | (no parallelism -- single worker) | baseline reference |
| `shared_memory` (`_omp` / `_sm`) | one address space -- workers read/write the **same buffers** (zero-copy) | a coherent, shared-memory machine |
| `message_passing` (`_mpi` / `_mp`) | **explicit copies** between disjoint buffers via a mailbox | a non-coherent / distributed machine |

> **Naming is by *data model*, not by API.** "shared_memory" and
> "message_passing" describe how data moves, not which threading library is
> used. PIMID models the *timing* of these two communication styles; it does
> not require (or fully implement) the OpenMP or MPI standards.

### How each variant is realized

| folder | `shared_memory` | `message_passing` |
|--------|-----------------|-------------------|
| **pim_kernels**, **host** | OpenMP threads over one address space (`#pragma omp`, `g++ -fopenmp`) | MPI ranks, built with `mpicxx`. Under `--method exec` the ranks run as threads of one process with `libpimid_mpi.so` loaded in place of the host's MPI library and a shared-memory mailbox transport (thread-MPI); the trace method runs them as processes. |

> **Build note.** The `message_passing` variants need an MPI C++ wrapper for
> `<mpi.h>`; the Makefile auto-discovers `mpicxx` and skips those targets with a
> note if none is found. `serial`/`shared_memory` build with `g++`.

## Random inputs

Every kernel that draws an index, a key, a column or a value over a range larger than 32,767 takes it from splitmix64
(Steele, Lea and Flood, "Fast splittable pseudorandom number generators", OOPSLA 2014), a 64-bit generator seeded as the
kernel documents (42 for bfs, radix and quicksort; 271828 for cg; 42 and 42 + 1000 t per thread for canneal). A draw
over a range R is the output reduced modulo R; the bias is at most R / 2^64 and is ignored. The affected draws are the
bfs edge targets (all PIM and host variants), the cg column indices, the canneal element choices, the radix keys (the
high 32 bits of one output) and the quicksort values (uniform over [0, 2^31)). Draws over small ranges (histogram bins,
net sizes, grid positions, acceptance tests) keep the 32-bit LCG. The bfs graph is a random graph of V vertices with
`--degree` out-edges each; from vertex 0 it reaches 209,646 of 209,715 vertices in 10 levels and 838,567 of 838,859 in
11.

The message-passing bfs (PIM kernel `bfs_mpi` and host `bfs_message_passing`) partitions the graph by vertex blocks:
with B = ceil(V / P), rank r owns the vertices [r*B, min(V, (r+1)*B)) and holds only their CSR rows and dist entries,
so a rank's memory and work are proportional to V / P. The graph is the one the serial and OpenMP versions build: a
rank starts the generator stream at its first row (draw k of splitmix64 has state seed + k * gamma), so the graph does
not depend on the number of ranks. The search is level-synchronous: in each level a rank expands its frontier,
marks a neighbour in its own block at once and sends every other neighbour to the neighbour's owner (the
per-owner counts by `MPI_Alltoall`, the vertices by one `MPI_Sendrecv` per rank pair); the owner keeps the
vertices it has not visited yet, and an `MPI_Allreduce` of the frontier sizes ends the search. A rank needs about 28 ints per owned
vertex at degree 8 (its rows, its dist, two frontiers, the send buckets and a receive buffer sized by the edges into
its block); on a device the whole set goes in the rank's PE slot. A set larger than the slot is refused at data
preparation, and the message names the largest `--vertices` that fits. That size is computed from the mean number of
in-edges per block, while the check uses the rank's own receive buffer, so a size within about 0.02% of the named one
can still be refused.

## Running

- **pim_kernels** / **host**: a device-only configuration (no hosts), select the data model with
  `--workload-type {serial|openmp|mpi}` (openmp -> shared_memory binary,
  mpi -> message_passing binary). Host vs device is chosen by the config's
  core type + placement (`ooo_core`/`HOST_MC` vs `alu_core`/`BANK`).
- **co-simulation**: the same binaries under a configuration with `system.hosts[]`:
  the ROI runs on the device PEs and the rest on the host.

See [cosim.md](cosim.md) for the host-device link model.

## Reading the cycle metric

A parallel (OMP or MPI) run leaves one `cycles: N # Simulated cycles` line per
device PE in `zsim.out`. **The first such line is core 0 only** -- a PE's
per-core count reflects only its own active cycles, and the kernel finishes
when the last PE finishes. **Never use the first `cycles:` line as the kernel
metric**: latching onto it (`grep cycles | head -1`, and the older
`parseZSimOutputFile()`) is the pre-1.8.8 defect that manufactured a spurious
bfs HBM3 32-PE cycle spike -- core 0 happened to be a low outlier at 16/64 PEs
but representative at 32, so recording it made 32 look like a step.

Use the **critical-path max** across PEs instead:

- **OMP device runs** now emit an aggregate summary
  `OMP cycles: <max> (mean, min, pes, critical-path max)` plus a
  parser-compatible `Total: <sum> cycles (max: <max>)` line (1.8.8). This
  mirrors the aggregation the MPI path already reported as `Total: ...
  (max: N)`. Purely additive -- the per-PE `cycles:` lines, `out.cycles`, and
  power analysis are untouched.
- **The kernel metric is the `(max: N)` value** on either path, not the first
  per-PE line. Harnesses must read `(max: N)`, not `grep cycles | head -1`.

Since 1.12.18 the run's cycles are its run time, the ROI's elapsed wall-clock
time, and every time-based power term uses the same window. An OpenMP device
run prints `OMP busy cycles: <max> (mean, min, pes, per-PE activity; busy
max)`, then `Run time: <W> cycles = <source>; busy max <max>`, then
`Total: <sum> cycles (max: <W>)`: the `(max: N)` figure is the run time, no
longer the busiest PE. A message-passing run prints `Run time:` after its
`Total:` line; its run time is the latest rank's ROI-relative end, which
equals its `(max: N)`. Each rank's ROI starts where it leaves the barrier on
the line before rank 0's roi_begin, after the barrier's own cost (since
(1.12.199)). The kernels call roi_end on rank 0 just before a
closing barrier; the ROI ends at the last rank's arrival at that barrier, so
every rank's kernel is inside it, whether the ranks run on device PEs or on
the host cores of a no-offload baseline. The per-PE `cycles:` lines are busy
activity.

## The pointer chase: load-to-use latency

`pim_kernels/pointer_chase` measures the memory latency a core sees, the
application's view of the memory. A random cyclic permutation over `--lines`
cache lines (Sattolo's algorithm from `--seed`, default 12345, so every run
builds the same chain) is laid out as a linked list, one 64-byte line per node.
In the ROI each thread (OpenMP) or rank (MPI) follows the chain for `--steps`
loads; every load depends on the one before it, so

    load-to-use latency = ROI cycles / steps

on the clock of the core that runs it. OpenMP thread t of T starts at position
t x lines / T of the one shared chain (the segments do not overlap while steps
<= lines / T), so T threads put T independent misses in flight; each MPI rank
builds its own copy of the chain. `BENCH_CHECKSUM` is the sum of the line
indices the chains end on.

- Keep the working set (lines x 64 B) well above the last-level cache: the
  default 1,048,576 lines are 64 MB, twice the 32 MB L3 of the host baselines.
- Give the chase enough steps to span many replay epochs (40,000 cycles each):
  the 50,000 steps of the large tier take 16 million host cycles on one DDR5 host core (324 cycles per step).
- The chain is built before the ROI and is not relocated into a PE's unit (no
  device-organization prep), so on the device it measures the access path of
  the placement as configured, not a near-data layout.
- Host baseline example (4 host cores, DDR5):
  `PIMID_COSIM_NO_OFFLOAD=1 OMP_NUM_THREADS=4 pimid --method exec --config <baseline yaml>
  --workload benchmarks/pim_kernels/pointer_chase/pointer_chase_omp --lines 1048576 --steps 50000
  --workload-type openmp`.

The run's statistics give the two other views of the same accesses: the
latency charged to the core at the memory interface (host: `mem-0` `rdlat +
wrlat` over `rd + wr`, which includes the host-path adder printed as
"host-path adder N cycles"; device: `pe-mi-*` `replayLat / replayPriced`) and
the memory simulator's own mean (`dramReplay` `hostLatencySum / hostRequests`,
`latencySum / ctrlRequests`).

## Parallel runtime on PEs (PIM runtime primitives)

1.12.18. On a device PE the OpenMP and MPI runtimes
are priced "the PIM way": the runtime's own code is not executed on the PE,
and each runtime event is charged the PIM primitive a PIM device would use
(UPMEM's measured primitives: lock acquire/release, handshake, and the barrier
of threads that share one PE; a barrier or launch among PEs is a dissemination
barrier or a binomial broadcast over the NoC). The
kernel's work -- including user code in a critical section, the inline atomics
of `#pragma omp atomic` and of a scalar `reduction` clause, the reduce
arithmetic of an MPI reduction, and every byte a message or collective moves --
stays fully simulated. Host cores keep executing their runtime (a CPU really
runs libgomp); `simulation.pim_runtime.apply_to: all` changes that. Keys,
defaults and sources: [yaml_reference.md](yaml_reference.md#pim-runtime-primitives-simulationpim_runtime).

How the runtime is told from the kernel:

- **OpenMP (libgomp)**: by address range. The executable mappings of
  `libgomp.so` are found in the guest's memory map; a thread is in the runtime
  from the moment it jumps from the workload binary into libgomp until control
  reaches the workload binary again (the outlined region body, or the return of
  the `GOMP_*` / `omp_*` call). Library code called from either side (glibc:
  `malloc`, `pthread_create`, futex) belongs to the caller. The event is the
  exported libgomp function the jump lands on (from libgomp's dynamic symbol
  table); the return of a region body into libgomp is the region's implicit
  barrier. No interposer library or relinking is needed and every libgomp
  entry point is covered; unsupported ones (tasks, target, teams, cancel)
  refuse by name.
- **MPI (`libpimid_mpi`, thread mode)**: the shim marks its own bookkeeping
  and announces each protocol event; its data temporaries are per-rank scratch
  buffers allocated once (no `malloc`/`free` per call) and stay priced, since
  they hold message payload and reduction operands.

The run prints the parameters in force ("Locks and handshakes assume
DPU-style atomics across the device's PEs", and the NoC barrier and launch for
all the device's PEs) and, per core, `[pim-runtime] ROI core N: events
(count/cycles): ... | primitive cycles charged C | runtime code not executed
on the PE: I instrs, M memory accesses`, then a `[pim-runtime] ROI total:`
line. `simulation.pim_runtime.enabled: false` restores the earlier model (the
runtime executed and priced like kernel code).

## Device-organization-aware data prep (near-data placement)

The simulator prices each PE access purely by data location (own unit = fast,
elsewhere = network distance) and never moves data itself -- placing data
near its PE is the benchmark's job, exactly as it is the programmer's job on
real PIM hardware. PIMID appends the device organization to the workload's
command line (`--placement --pes --total-units --pages-per-unit`; a kernel that
does not read them ignores them), and
`benchmarks/include/pimid_devorg.h` gives kernels the address math to
relocate each PE's working set into that PE's own placement unit before the
ROI (plain untimed setup; the measured kernel arithmetic is byte-identical).
The five kernels of the co-simulation experiment (`stream_triad`, `gemv`,
`bfs`, `stencil_2d`, `histogram`) do this: partitioned data goes to the owner's slot, read-shared
data is replicated, and genuinely cross-PE traffic (stencil halos, bfs edge
scatter) stays remote -- so it pays real network distance, which is the
point. Coarse/host-shared placements (`CHANNEL`, `LOGIC_DIE`) need no prep
and run the original path; a working set too large for a PE slot falls back
to host layout with a note. MPI variants need no prep for rank
locality: each rank touches its own data first, so its pages live in its own
PE's memory (first-touch placement, [memory.md](memory.md#pe-placement-levels)).

Since 1.12.18 placement is first touch, so a slot belongs to a PE only if that
PE writes it first. The shared-memory kernels therefore fill each slot from its
own thread (thread p fills PE p's slot), and on the host-layout path each thread
initialises the share of every array it later computes on, with the same split
as the compute loop. Data built by one sequential random stream (bfs, histogram,
spmv) is first zeroed by its owners, then filled. A PE's pages also fill its
memory in the order it first touches them, so the message-passing kernels build
their data in the slot itself: a setup copy built elsewhere and copied in would
be touched first, hold the PE's own unit, and push the data the kernel reads
into the next one. Unmodified programs that set data up serially (Rodinia, NPB)
place it with the master's PE, as they would on a real non-uniform machine.

## The PE scratchpad

Since 1.12.18 the compute unit (`alu_core`) has a small data RAM of its own,
`pim.pe.spm_bytes` (default 4096; the published reference point is UPMEM's
64 KB WRAM). A load or store inside it costs the RAM's CACTI access time; every
other access still goes to the device memory, one access at a time. As on real
PIM hardware nothing enters the RAM by itself: the kernel moves blocks in and
out through `benchmarks/include/pimid_spm.h`:

    pimid_spm_t s;  pimid_spm_open(&s);       /* once per thread, before the ROI */
    const float* a = (const float*)pimid_spm_in(&s, off, src, bytes);   /* memory -> RAM */
    float* o = (float*)pimid_spm_out(&s, off, dst);                     /* a RAM area to fill */
    pimid_spm_flush(&s, dst, o, bytes);                                 /* RAM -> memory */
    pimid_spm_close(&s);                      /* after the ROI */

`pimid_spm_tile(&s, nbuf, elem)` gives the elements per buffer when the RAM is
split into `nbuf` equal buffers. `pim.pe.spm_staging` decides who moves a block:
the PE's DMA engine (`dma`, default; no copy instructions) or the PE itself
(`core`). Where there is no scratchpad -- `spm_bytes: 0`, an in-order or
out-of-order PE, a native run -- `pimid_spm_open` reports 0, `pimid_spm_in`
returns the source pointer, `pimid_spm_out` the destination, flush does nothing
and the tile is the whole range, so the same kernel code runs on the memory
directly. Outside the simulator, `PIMID_SPM_CHECK_BYTES=<n>` runs the tiled path
natively with the PE copying, to check a kernel's tiling against its untiled
result.

The PE's own stack is in its DRAM by default (`pim.pe.stack: dram`), so a
register the compiler spills in a tiled loop costs a memory access. With
`pim.pe.stack: spm` the stack lives in the scratchpad instead, as on UPMEM,
and keeps `pim.pe.spm_stack_bytes` of it (default 8192): `pimid_spm_open`
then reports `spm_bytes - spm_stack_bytes` for the buffers. Each PE reports
the stack span it touched in the ROI as `stackSpanBytes`, which is what the
reserve must hold. The default reserve holds the ROI stack of every shipped
kernel (at most 3,736 bytes, a message-passing rank's).

The eight PIM kernels other than `pointer_chase`, in their serial, shared-memory
and message-passing forms,
go through one tiled routine per kernel (the same text in all three forms).
Data read once streams through the RAM in tiles; data that is reused stays in
it (gemv's x tile, histogram's bins when they fit). Irregular gathers --
spmv's `x[col]`, bfs's `row_ptr[u]` and `dist[v]` -- stay direct memory
accesses. Buffers handed to MPI are always ordinary memory.

## NPB (NAS Parallel Benchmarks)

Self-contained single-file C implementations of 5 NPB kernels with zsim
hooks, in `benchmarks/npb/`:

| Kernel | Algorithm | Memory Pattern |
|--------|-----------|----------------|
| **IS** | Integer Sort (bucket sort + ranking) | Random scatter (histogram-like) |
| **CG** | Conjugate Gradient (sparse CG with CSR SpMV) | Indirect gather + streaming |
| **EP** | Embarrassingly Parallel (Gaussian pairs) | Pure compute, minimal memory |
| **MG** | Multi-Grid (3D V-cycle) | 3D stencil + multi-scale |
| **FT** | 3D FFT (Cooley-Tukey radix-2) | Strided butterfly access |

`make -C benchmarks/npb` places binaries in each subdirectory (`is/is`,
`cg/cg`, ...). Run configs live in `benchmarks/npb/configs/` as
`<kernel>_class<S|W|A>_<omp|mpi>.yaml` (5 kernels x 3 classes x 2 variants
= 30 files):

| Class | IS | CG | EP | MG | FT | max_instructions |
|-------|----|----|----|----|----|----|
| S | 4,096 | 256 | 256 | 16 | 16 | 10M |
| W | 65,536 | 1,024 | 4,096 | 32 | 32 | 100M |
| A | 1,048,576 | 4,096 | 65,536 | 64 | 64 | 1B |

`./run_npb.sh` runs all of them (`PIMID_BIN=/path/to/pimid` overrides the
binary). Each benchmark also runs standalone without PIMID, e.g.
`./is/is --size 1024 --threads 4`.
